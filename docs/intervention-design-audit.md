# Mentication Intervention Design Audit

Scope: the 17 intervention boards in `Mentication Structure-4.png`, the individual boards available in the project and supplied asset folder, and all supporting visual sheets currently available. This is a design/content audit only. No app code or final production artwork has been changed.

## Executive decision

All 17 interventions now have canonical directions. Eight are close to approval and nine require targeted amendments before final asset generation; none remain conceptually unresolved.

The main risks are not visual polish. They are:

1. Safety checks occur too late in Urge Surfing and Test the Prediction.
2. Personalisation and learning claims are more specific than the current designs explain or can safely infer.
3. Several otherwise complete boards are missing production asset sets.
4. Shared controls, accessibility behaviours and data/privacy expectations are inconsistent across the library.

## Status legend

- **A — Approve with minor amendments:** preserve the concept and flow.
- **B — Targeted redesign:** preserve the core mechanism but change important screens, rules or visual behaviour.
- **C — Resolve before production:** canonical concept, safety model or product capability is not yet settled.

## Cross-library rules to add before regeneration

### 1. Shared intervention shell

Every intervention should use the same placement and behaviour for exit, pause, mute, captions, reduced motion, “this is not helping,” and emergency/support handoff. The inner experience can remain highly distinctive.

### 2. State and suitability gate

Only show a gate where it changes the intervention. It must occur before the risky mechanism, not at the end. The highest-priority additions are Urge Surfing, Test the Prediction, PMR, Then What? and Change the Scene.

### 3. Honest outcomes

Completion must mean the user completed or deliberately stopped the process—not that they became calm, productive, happy or certain. Preserve “unchanged,” “partly,” “couldn’t start,” “not safe,” and “need another kind of help” as first-class outcomes.

### 4. Personalisation contract

For every feature that “learns,” specify:

- what explicit input is stored;
- what is inferred;
- how much evidence is required;
- how the user corrects or deletes it;
- whether it remains on-device or is sent elsewhere;
- what happens when confidence is low.

Use language such as “based on what you previously chose” rather than implying that the app has measured the nervous system, motivation, reward or safety.

### 5. AI suggestion boundaries

AI suggestions are drafts, not clinical judgments. The user confirms all labels, thought classifications, experiment designs, message wording, task steps and activity recommendations. There must always be an edit, reject or different-option route.

### 6. Accessibility baseline

All interventions require high-contrast text, Dynamic Type/reflow, screen-reader labels, captions or text equivalents, sound-off and haptics-off modes, and a reduced-motion version. Drag, hold, trace and slide interactions need a tap/button alternative. Meaning cannot rely on colour alone.

### 7. Science and psychoeducation

Keep in-experience psychoeducation to one or two lines. Use restrained claims tied to the actual mechanism, not the visual metaphor. Maintain a separate internal evidence register for sources and review dates; citations do not need to occupy the active intervention screen unless a user opens “Learn why.”

### 8. Audio baseline

Audio should begin predictably at a conservative level, duck under narration, contain no sudden peaks, and expose mute/stop immediately. Sleep experiences need background playback and lock-screen behaviour defined before design approval.

### 9. Shared visual grammar

Retain the distinct metaphors, but standardise the functional layer: type scale, safe areas, control dock, progress language, selection states, back/exit behaviour and button hierarchy. Several concepts currently feel like different premium apps rather than rooms within one premium app.

### 10. Production asset specification

Final generation should produce component-ready assets, not phone screenshots: clean backgrounds, transparent foreground objects, motion layers, state variants, reduced-motion stills and exact crop/aspect specifications. Text and controls should remain native app UI rather than baked into raster artwork.

## Canonical decisions

1. **Resolved — Thought or Fact:** softened Mind Court visual world with the notebook system's fact/interpretation/prediction mechanics.
2. **Ignition Point — resolved:** this is the new name for Pleasure, Mastery or Connection, and Dream remains as its permanent fourth pathway.
3. **Night Channel — resolved:** Familiar Replay may point to any user-chosen familiar media. Mentication audio plays natively; saved external media uses honest bookmarks/handoffs; no voice cloning or unsupported external playback control.

## Recommended amendment order

1. Fix safety sequencing for Urge Surfing, Test the Prediction, PMR and Then What?.
2. Write one shared personalisation/privacy contract and apply it to every “memory,” “map,” “record” and “profile.”
3. Standardise the shared shell and accessibility behaviours.
4. Amend each board in place.
5. Approve the 17 revised flows.
6. Generate only the missing or changed production assets.
7. Build the shared UI shell and reusable experience engines before coding intervention-specific variations.
